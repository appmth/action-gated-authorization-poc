# コンテキストの受け渡し設計

## 課題の背景

業務ロジックから認可を切り離す際、認可エンジン側が「今、どういう業務文脈（Context）でこの操作が行われようとしているか」をどうやって正確に受け取るか、という実装上の難易度が課題となる。

### 重要な論点

めちゃ重要な論点。AGAの「詰まる場所」はだいたいここです。

**結論**: "正確なContextを受け取る"を目標にしすぎると破綻しやすいので、設計上は Contextを"証拠（Evidence）"として分解して、信頼度を段階化するのが現実的。

---

## 何が難しいのか（問題の正体）

認可エンジン（PDP/OPA）が欲しいのは「状況」だけど、アプリが出せるのは多くの場合「主張」です。

- **目的（purpose）**: ユーザー/Agentが「これが目的です」と言うだけだと嘘が混ざる
- **状態（state）**: DBやワークフローの状態とズレると判断が壊れる
- **時間/場所/端末**: クライアント申告は信用できない
- **問い合わせ起点**: 会話文脈をそのまま渡すと曖昧・長い・再現不能

**だから「業務文脈を渡せ」と言うと、実装は泥沼化する。**

---

## 解き方：Contextを"分解"して、信頼できる順に積む

Contextを1個の塊で渡さず、**3層に分ける**のがコツ。

### ① Immutable（不変・検証可能）

PEP側で作れる/検証できるものだけ。

- **principal（誰）**: sub, client_id, actor 等（Auth0のトークン由来）
- **action（何を）**: tool名、API名、操作種別
- **resource（どれに）**: resource_id、tenant_id など
- **time（いつ）**: サーバ時刻
- **channel（どこから）**: 呼び出し元サービスID、実行環境

> ✅ ここは"嘘が入りにくい"ので認可の主軸にできる

### ② Derived（導出・参照で確定できる）

アプリが主張しなくても、PEP/PDPがデータ参照で確定できるもの。

- **resourceの属性**: PIIフラグ、所有者、機微度
- **workflowの段階**: 受付中/審査中/決裁済
- **relationship**: 担当者/上長/閲覧許可
- **risk signals**: 深夜、短時間多回数など ※サーバ観測

> ✅ "業務文脈"のコアはここに寄せると安定する

### ③ Claimed（申告・曖昧）

ユーザー/Agentが言う目的や理由。

- **purpose**: 住民問い合わせ対応のため、など
- **justification**: この情報が必要、など
- **free-textなメモ**

> ⚠️ 単体では信用しない。ログ・レビュー・追加制約のトリガに使う。

---

## 「正確さ」の代わりに「再現性」を取りに行く

認可で一番重要なのは **"正確に理解した"** ではなく、監査で **"なぜ許可したか再現できる"** こと。

### PoCで強化すべきポイント

1. **PDP入力を構造化（JSON）して保存**
2. **PDP判断の理由（rule_id / matched_conditions）を保存**
3. **実行ログに request_idで紐づけ**（判断→実行→結果）

これで「説明責任が成立する構造」が見える。

---

## 実装パターン（PoCで勝てる最小形）

### パターンA：Contextは"参照"で作る（推奨）

```
1. Agent → PEPへ「action + resource_id + 最小パラメータ」
2. PEPが resource_id から 必要な属性を取得（PII/担当/状態）
3. それを OPAへ渡して判定
4. 許可ならPEPが実行
```

**メリット**: Agent/業務側がContextを"作らない"ので破綻しにくい

### パターンB：Context Token（署名付き）を発行する

業務側が「このケースは今こういう状態」とまとめた 署名付きContext を発行し、PEPが検証してPDPへ渡す。

- **メリット**: 分散システムで強い
- **デメリット**: PoCでは作り込みが増える

---

## "嘘の混入"をどう扱うか（AGAっぽい勝ち筋）

PoCでは、わざと「Agentが目的外のPIIを取りに行く」ケースを作って、以下のような流れを実装する：

| 要素 | 内容 |
|------|------|
| **Claimed目的** | 「ゴミ収集日の案内」 |
| **Derived属性** | 納税情報は機微度高、目的外 |
| **Policy** | 目的とデータカテゴリが合わなければ拒否 |
| **Audit** | 拒否理由に「purpose mismatch / sensitive category」出す |

**これが一番伝わる。**

---

## まとめ（あなたの指摘への答え）

はい、Context受け渡しは実装難易度の核。
でも解法は「業務文脈を正確に渡す」じゃなくて、

1. **Contextを Immutable / Derived / Claimed に分解**
2. **認可判断は Derived中心に寄せる**（参照で確定）
3. **Claimedは単体で信用しない**（監査/補助）
4. **判断入力と理由を保存して説明責任を成立させる**

この設計だと、AGAの思想（**"AIを信用しなくて済む構造"**）とも整合する。
