# AGA PoCデモスコープ
本 PoC では、**Action-Gated Authorization（AGA）** の有効性を示すために、  
証明対象を以下の **3点に厳密に限定**する。

網羅的な認可やフル IAM の再実装は目的とせず、  
**「これができれば、AGAという設計思想は成立する」** ことを示す最小構成とする。

---

## 証明対象①  
### AI Agent が生成した行動を「実行前」に止められること

**証明したいこと**

- AI Agent が自律的に生成した Action に対して
- API 境界や認証段階ではなく
- **実行直前のゲート（PEP）で許可／拒否できる**

**ポイント**

- 認証・トークン・ロールは正しい状態でも止められる
- 「認証できた＝実行してよい」という前提を崩す

**AGA との対応関係**

- Action 提案 → PEP → PDP → Allow / Deny
- 業務コードや Agent 内部に if を書かない

---

## 証明対象②  
### 同じ Action でも「業務文脈（Context）」によって判断が変わること

**証明したいこと**

- Action 名・対象・呼び出し元が同じでも
- **業務文脈（Context）** によって
- PDP の判断結果が変わる

**最低限扱う Context**

- `purpose`（業務目的）
- `time`（時間帯）
- `data_sensitivity`（PII 有無）

**ポイント**

- RBAC では表現できない判断軸
- 「なぜ今それをやるのか」に答えられる構造

---

## 証明対象③  
### なぜ許可／拒否したかを「人間に説明できる形」で残せること

**証明したいこと**

- 許可／拒否の結果だけでなく
- 判断に使われた Context とルールが
- **ログ・レスポンスとして明示的に残る**

**ポイント**

- 説明責任の最終地点を AI の内部に置かない
- 監査・レビュー・住民説明に耐える構造

---

## PoC で「あえて証明しないこと」

本 PoC では、以下はスコープ外とする。

- フル IAM / 認証基盤の刷新
- 高度な ReBAC グラフ
- 完全自律型 Agent
- UI の作り込み
- セキュリティの網羅性・完全性

**狙いは「思想と配置の正しさ」を示すこと**であり、  
実運用の完成形を作ることではない。

---

# 最小デモシナリオ（1本で3点を証明）

## シナリオ概要  
**自治体の問い合わせ対応 AI Agent**

住民からの問い合わせに対応する AI Agent が、  
業務データ（PII を含む可能性あり）へアクセスしようとする。

---

## デモで扱う Action

\```yaml
action: get_resident_info
description: 住民情報（PIIを含む可能性あり）を取得する業務アクション
\```

---

## Context パターン

### Context A（許可されるケース）

```json
{
  "purpose": "inquiry",
  "time": "business_hours",
  "data_sensitivity": "required"
}
```

**結果**

- PDP: Allow  
- PEP: Action 実行  

**理由ログ**

```
問い合わせ対応のため、営業時間内で必要最小限の PII アクセスであるため許可
```

---

### Context B（拒否されるケース）

```json
{
  "purpose": "inquiry",
  "time": "night",
  "data_sensitivity": "high"
}
```

**結果**

- PDP: Deny  
- PEP: Action 実行前にブロック  

**理由ログ**

```
問い合わせ目的に対して、深夜帯の高感度 PII アクセスは業務上正当化できないため拒否
```

---

## このデモで同時に示すこと

- Agent は **同一の Action** を生成している  
- 認証・権限は **同一**  
- 変わるのは **Context だけ**  
- それでも **実行可否が変わる**  
- その理由が **人間に説明可能な形で残る**

---

## PoC の一行まとめ

この PoC は、**AI Agent が生成した行動を、実行前・文脈依存・説明可能な形で制御できる**ことを示す。
